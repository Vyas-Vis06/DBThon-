# Table guide

A readable map of the 35 application tables in schema revision 0014. It complements the [ER diagrams](ER_DIAGRAM.md) and the
[database design](DATABASE_DESIGN.md). The generated [schema reference](SCHEMA_REFERENCE.md) remains the exact source for every
column type, default, constraint, index, trigger and row-level security policy; this guide explains why each table exists and
how it connects to the workflow.

## How to read the tables

PK is the primary key. FK names the referenced table; “many to one” means many rows here can point to one row there. Optional
foreign keys are marked “optional.” A composite foreign key is shown with both columns because the pair is the integrity
boundary. Actor columns link to the account that performed an action where the database actually defines that FK.

The six application roles are ADMIN, ENGINEER, SUPERVISOR, WORKER, CONTRACTOR and AUDITOR. API role checks and PostgreSQL RLS
both apply to the runtime role. ADMIN maintains users and configured thresholds and is included in shared municipal write
routes. Narrower actions stay explicit: only ENGINEER files a mechanisation waiver; only SUPERVISOR maintains permit crew,
gear and entry logs; SUPERVISOR/ENGINEER authorize or close permits; WORKER can stop work on their own permit; CONTRACTOR sees
its own work and can submit its own invoices; AUDITOR is read-only. The database owner used for migrations and local
demonstrations has wider rights than the API role. See [SECURITY.md](../SECURITY.md) for exact policies and their limits.

|---|---|---|---|
| [**role**](SCHEMA_REFERENCE.md#role) (role_id) | The seeded role catalogue; name is unique and uppercase. | One role to many app_user rows. | Reference data installed by migrations; it is not ordinary runtime policy data. |
| [**app_user**](SCHEMA_REFERENCE.md#app_user) (user_id) | A login identity: role_id, email, password_hash, is_active and optional ulb_id, contractor_id or worker_id scope. Email is unique; worker_id is unique when present. | Many accounts to one role; optional many-to-one links to ULB or contractor; a worker has zero or one linked login. Also referenced by session and actor columns throughout the schema. | Scope trigger requires contractor logins to map to a contractor, worker logins to a worker, and staff roles to neither. Password hashes are excluded from audit payloads. Account administration is an ADMIN task. |
| [**user_session**](SCHEMA_REFERENCE.md#user_session) (session_id) | Server-side session: user_id, unique token_hash, csrf_token, created_at, expires_at and revoked_at. The raw cookie token is not stored. | Many sessions to one app_user; deleting an account cascades to its sessions. | Expiry must follow creation. Logout, expiry and revocation are stored server-side; application sessions are managed by the authentication flow. |
| [**ulb**](SCHEMA_REFERENCE.md#ulb) (ulb_id) | Municipal body/zone with unique name, district and state. | One ULB to many manholes and machines; app_user may have an optional home ULB. | Geographic parent/reference data. Current ENGINEER and SUPERVISOR visibility is not restricted by ULB. |
| [**contractor**](SCHEMA_REFERENCE.md#contractor) (contractor_id) | Contractor identity, unique licence_no, licence_valid_until and status. | One contractor to many workers and jobs; incidents and alerts can retain a contractor reference. A contractor login can be scoped to one contractor. | Status is ACTIVE, SUSPENDED or BLACKLISTED. New work is blocked for an inactive, suspended, blacklisted or unlicensed contractor; changing contractor eligibility revalidates affected permits. ENGINEER/ADMIN maintain records; ADMIN has the broader deletion privilege. |
| [**worker**](SCHEMA_REFERENCE.md#worker) (worker_id) | Worker identity: contractor_id, unique namaste_id, active flag, medical_fit_until and trained_until. | Many workers to one current contractor; many-to-many with permits through permit_crew; incidents refer to workers. A worker has zero or one login. | Fitness, training and active status are checked at authorization and revalidated when credentials or employer change. ENGINEER/ADMIN maintain worker records; contractors and workers receive scoped reads. |
| [**manhole**](SCHEMA_REFERENCE.md#manhole) (manhole_id) | A sewer/septic access point: ulb_id, unique code, kind, depth_m, lat and lng. | Many manholes to one ULB; one manhole to many complaints and incidents. | Kind, positive depth and coordinate ranges are CHECK constraints. Operational identity is the stable code. |
| [**machine**](SCHEMA_REFERENCE.md#machine) (machine_id) | Municipal cleaning asset: ulb_id, unique code, kind and availability status. | Many machines to one ULB; one machine to many deployment records over time. | Kind and status are constrained. Deployment history records attempts and outcomes; machine status itself is not a proof that a job was cleared. |

## Complaints, jobs and mechanised work

| Table (PK) | Purpose and notable columns | Relationships and cardinality | Main database controls and lifecycle |
|---|---|---|---|
| [**resolution_type**](SCHEMA_REFERENCE.md#resolution_type) (code) | Resolution catalogue with description and requires_evidence. It defines which closed outcomes should leave clearance evidence. | One resolution type to many complaints. | A resolution with requires_evidence=false is intentionally outside the detection population; exemption is data-driven. Seeded reference data. |
| [**complaint**](SCHEMA_REFERENCE.md#complaint) (complaint_id) | The reported blockage: manhole_id, description, raised_at, status, resolved_at, resolution_code and resolved_by. | Many complaints to one manhole; optional many-to-one resolution type and resolving app_user; one complaint to many jobs and alerts. | CHECKs require resolved time and resolution code exactly when status is RESOLVED and prevent resolution before raise time. ENGINEER/ADMIN manage complaints; access to a complaint can also flow through an assigned contractor or worker's job. |
| [**job**](SCHEMA_REFERENCE.md#job) (job_id) | Work order: complaint_id, contractor_id, method, status and optional created_by account. | Many jobs to one complaint and one contractor; created_by points to app_user; one job to many machine deployments, permits and invoices; each job has zero or one waiver. | Method is MECHANISED or MANUAL_EXCEPTION. Insert and method-change guards enforce eligible contractors and the waiver path. ENGINEER/ADMIN create or reassign jobs; contractors see their own. |
| [**machine_deployment**](SCHEMA_REFERENCE.md#machine_deployment) (deploy_id) | A machine attempt: job_id, machine_id, started_at, ended_at, outcome, recorded_by, row receipt recorded_at and final-outcome receipt outcome_recorded_at. | Many deployments to one job and one machine; recorded_by points to an app_user. | End time and outcome must agree. An outcome is finalized once and cannot be rewritten. The server receipt of the final result, not a backdated field time or original deployment-row receipt, determines timely SE1 machine evidence. ENGINEER/ADMIN record deployments. |
| [**mechanisation_waiver**](SCHEMA_REFERENCE.md#mechanisation_waiver) (waiver_id) | One written exception per job: reason_code, justification, approved_by and approved_at. | Unique job_id makes this zero or one waiver per job; many waivers may be approved by one ENGINEER account. | Justification must be at least 50 characters; MACHINE_FAILED needs a failed deployment on the complaint. Insert is ENGINEER-only and the waiver is append-only. A permit cannot be drafted without it. |

## Permit, safety evidence and policy provenance

| Table (PK) | Purpose and notable columns | Relationships and cardinality | Main database controls and lifecycle |
|---|---|---|---|
| [**entry_permit**](SCHEMA_REFERENCE.md#entry_permit) (permit_id) | The permission record: job_id, supervisor_id, status, authorised_at, authorised_by, valid_until, ended_at and end_reason. | Many permits to one job; many-to-one links to supervisor and optional authorizing account. One permit can have many crew assignments, gas readings, safety events and entries; it has zero or one authorization snapshot. Entries link through permit_crew; gas readings link directly to the permit. | Starts DRAFT. Only DRAFT→AUTHORISED through the clause gate, DRAFT→CANCELLED, or AUTHORISED→CLOSED/ABORTED. CHECKs align status and timestamps. Supervisor creates the permit; supervisor/engineer may attempt authorization, but PostgreSQL rechecks every path. Crew and gear freeze after authorization. |
| [**permit_crew**](SCHEMA_REFERENCE.md#permit_crew) (permit_id, worker_id) | Junction table that assigns a worker and exactly one crew_role (ENTRANT, STANDBY or SUPERVISOR) to a permit. | Each row belongs to one permit and one worker; permits and workers are many-to-many through this table. Its composite key is also the parent key for gear_issue, entry_log and incident crew membership. | The composite PK prevents assigning the same worker twice to one permit, including two roles. Crew size/role requirements are checked before authorization. SUPERVISOR maintains DRAFT crew; rows freeze after authorization. |
| [**gear_item**](SCHEMA_REFERENCE.md#gear_item) (gear_code) | Protective equipment catalogue: name, statutory flag and legal_ref. | One catalogue item to many gear_issue rows. | Uppercase stable code. The illustrative statutory set is read by relational division; an empty required set fails closed. ADMIN maintains the catalogue. |
| [**gear_issue**](SCHEMA_REFERENCE.md#gear_issue) (issue_id) | Evidence that one gear item with serial_no was issued to one crew member on one permit; includes issued_by and issued_at. | Many-to-one to the exact permit_crew pair and gear_item; issued_by references app_user. | UNIQUE (permit_id, worker_id, gear_code) means one issue row per item/person/permit. Composite FK prevents issuing to a non-crew member. SUPERVISOR issues gear on DRAFT permits; issue rows freeze on authorization. |
| [**gas_detector**](SCHEMA_REFERENCE.md#gas_detector) (detector_id) | Detector identity: unique serial_no, model and calibration_valid_until. | One detector to many gas_reading rows. | A reading is refused when the detector calibration had lapsed on the reading date. ADMIN maintains detector records; calibration changes revalidate permits that rely on that detector. |
| [**gas_reading**](SCHEMA_REFERENCE.md#gas_reading) (reading_id) | Append-only measurement: permit_id, detector_id, depth_level, o2_pct, h2s_ppm, lel_pct and co_ppm, taken_at, recorded_by and server recorded_at. | Many readings to one permit and one detector; recorded_by points to app_user. | Depth and physical value ranges are CHECKed. Insert guard checks calibration, actor and permit state. Authorization requires the latest in-scope TOP, MID and BOTTOM readings to be fresh and within configured limits; a newer bad reading cannot be hidden by an earlier good one. SUPERVISOR/ENGINEER record readings. |
| [**entry_log**](SCHEMA_REFERENCE.md#entry_log) (entry_id) | A worker's physical interval: permit_id, worker_id, period, recorded_by, recorded_at and exit_recorded_at. | Many-to-one to the composite permit_crew key and to recorded_by. One crew member may have multiple intervals on a permit. | Only an ENTRANT can be logged. A trigger checks current permit, validity, daylight, work-stretch/rest and truthful exit rules. GiST exclusion constraint ex_entry_no_overlap prevents a worker's intervals from overlapping across permits. Deletes are refused; a real exit can still be recorded after a stop and any violation is retained as a safety event. SUPERVISOR records intervals. |
| [**legal_clause**](SCHEMA_REFERENCE.md#legal_clause) (clause_code) | The gate checklist catalogue: title, display legal_ref and sort_order. | One clause to many legal_clause_source links. Gate functions look up clause titles; they do not FK to a parameter row. | Clause order is unique; code is uppercase. Migration-managed checklist data. |
| [**policy_source**](SCHEMA_REFERENCE.md#policy_source) (source_code) | A classified citation record: source_type, title, source_url, source_version, citation_clause and applicability. | One source to many legal_clause_source links, current parameters and parameter history. | source_type distinguishes LAW, COURT_DIRECTION, GUIDANCE and PRODUCT_POLICY. Immutable for the runtime role; this keeps applicability context visible and prevents silently rewriting a citation. |
| [**legal_clause_source**](SCHEMA_REFERENCE.md#legal_clause_source) (clause_code, source_code) | Link table connecting each gate clause to one or more classified sources, with per-clause sort_order. | Many-to-many between legal_clause and policy_source. | Composite PK prevents duplicate links; sort order is unique within each clause. Migration-managed and append-only. |
| [**rule_parameter**](SCHEMA_REFERENCE.md#rule_parameter) (param_key) | The current configured value: numeric value, unit, description, legal_ref, is_assumption, source_code, revision, updated_by and updated_at. | Many parameters to one policy_source; updated_by references app_user. | ADMIN changes the value with a written reason. A trigger increments revision and appends rule_parameter_history in the same transaction. Gate and detection functions read this table rather than embedding mutable thresholds in application code. |
| [**rule_parameter_history**](SCHEMA_REFERENCE.md#rule_parameter_history) (history_id) | Immutable revision record: param_key, revision, value, source_code, effective_at, actor_user_id and change_reason, plus the descriptive value fields. | Many history rows to one parameter and one policy_source. Unique (param_key, revision). | Append-only. Migration 0014 wrote a baseline for current values because prior revision history did not exist; it does not reconstruct older policy intervals or replay old decisions by itself. |
| [**permit_authorization_decision**](SCHEMA_REFERENCE.md#permit_authorization_decision) (decision_id) | One successful permit decision snapshot: unique permit_id, actor_user_id, decision_at, JSONB snapshot, snapshot_format and snapshot_sha256. | Zero or one row per permit (unique permit_id); FK to entry_permit with delete restricted. | Inserted by the database after successful authorization and immutable. Captures clause results, evidence identifiers, policy revisions and cited source classifications. The digest is an integrity check inside the database trust boundary, not an external signature or proof that sensors were truthful. |
| [**permit_safety_event**](SCHEMA_REFERENCE.md#permit_safety_event) (event_id) | Durable local safety event: permit_id, optional entry_id, unique event_key, event_type, reason_code, detail and occurred_at. | Many events to one permit; optional many-to-one link to entry_log. This event history preserves what the system observed without claiming an external alert was delivered. |

Partial unique indexes allow at most one hold per invoice/source. | Holds are source-linked. Dismissing an alert releases only its alert holds; an incident hold uses a separate reasoned release. | [**detection_rule**](SCHEMA_REFERENCE.md#detection_rule) (rule_code) | Catalogue and enable switch for SE1 and SE2 evidence-gap rules. | One detection rule to many shadow_entry_alert rows. | Rule code format is checked. | [**shadow_entry_alert**](SCHEMA_REFERENCE.md#shadow_entry_alert) (alert_id) | Persisted suspicion: complaint_id, rule_code, contractor_id snapshot, status, reason, evidence_deadline, detected_at and review fields. | Many-to-one to complaint, detection_rule and optional contractor; reviewed_by references app_user. ## Relationship paths worth knowing

The central work chain is **ulb → manhole → complaint → job → permit → crew → gear/entries**. Gas readings link directly to the permit, while gear and entry logs link through the permit's crew. A complaint can have multiple jobs, so a later machine success on any job can be evidence for the same complaint. A permit is a job-scoped safety authorization, not a replacement for the complaint or work order.

The two many-to-many relationships are explicit junction tables: permit↔worker via **permit_crew**, and legal_clause↔policy_source via **legal_clause_source**. The first junction carries the worker's role for this permit and is the composite-FK boundary for gear, entries and incidents. The second carries citation ordering.
